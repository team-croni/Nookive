# Search Evaluation

검색 순위 변경이 실제로 검색을 좋게 만드는지 확인하기 위한 두 단계 평가 체계입니다.

| 단계 | 위치 | 실행 | 목적 |
|---|---|---|---|
| 회귀 평가셋 | `src/features/search/evaluation/` | `npm test` (CI 포함) | 작은 합성 코퍼스로 순위 회귀를 즉시 감지 |
| 공개 벤치마크 | `scripts/eval/public/`, `public.test.ts` | 로컬에서 필요할 때 | 실제 규모·실제 데이터에서 게이트와 가산점이 도움이 되는지 확인 |

두 단계 모두 앱과 같은 순위 파이프라인(`rankQuery` → `orderResultsBySection`)을 실행하며, 지표 정의는 `metrics.ts` 한 곳에서 관리합니다.

---

## 1. 회귀 평가셋 (CI)

- 문서·PDF·이미지·오디오·비디오·폴더로 구성된 합성 코퍼스(55개 항목), 실제 Mac 규모의 앱 레코드 194개, 정답이 표시된 쿼리 93개.
- 사전 계산한 벡터(`fixture.json`)를 쓰므로 CI에서 모델 없이 실행됩니다.
- 기준선(`baseline.json`)보다 지표가 나빠지면 실패합니다. 사용법은 `CONTRIBUTING.md`의 "Search evaluation set"을 참고하세요.
- 검색 개인화(열어본 결과 가중치)는 넣지 않고 기본 랭킹만 측정합니다. `rankQuery`에 `boost`를 넘기지 않으면 개인화가 꺼집니다.
- 한계: 코퍼스가 작고 쿼리를 같은 작성자가 만들었기 때문에, z-score 게이트처럼 인덱스 전체 분포에 의존하는 동작은 이 평가셋만으로 판단하지 않습니다.

## 2. 공개 벤치마크 (로컬)

### 준비와 실행

```bash
npm run sidecar                            # 임베딩 서버 (127.0.0.1:8080)
npm run eval:public:prepare -- miracl      # 약 230MB 다운로드, 문단 약 4,800개 색인
npm run eval:public:prepare -- xm3600      # 약 330MB 다운로드, 사진 600장 색인
npm run eval:public:prepare -- mixed       # 위 두 데이터셋을 하나의 인덱스로 합침
npm run eval:public -- mixed               # 결과 표 출력 + report.md/report.json 저장
```

- 데이터와 결과는 `~/Library/Caches/nookive-eval/`에만 저장되며 저장소에 커밋하지 않습니다.
- 표본은 해시로 고르기 때문에 매번 같은 쿼리·방해 문단·사진이 선택됩니다.
- 옵션: `--queries N`(MIRACL 쿼리 수), `--distractors N`(MIRACL 무작위 방해 문단 수, 기본 2000), `--images N`(사진 수, 기본 600).

### 비교하는 세 가지 방식

| 방식 | 설명 |
|---|---|
| `nookive` | 앱과 같은 전체 파이프라인 (모달리티별 z-score, 절대 하한, 키워드 가산점, 파일 단위 그룹화, 섹션 정렬) |
| `cosine` | 게이트 없이 파일별 최고 코사인 유사도 순 상위 20개 |
| `keyword` | 임베딩 없이 키워드 검색만 |

### 데이터셋

| 데이터셋 | 구성 | 정답 |
|---|---|---|
| MIRACL (ko, dev) | 쿼리 213개. 사람이 판정한 문단(정답과 오답 후보) 약 2,800개 + 무작위 위키백과 문단 약 1,950개 | 사람이 정답으로 판정한 문단 |
| Crossmodal-3600 | 사진 600장. 사진마다 한국어 캡션 1개, 영어 캡션 1개를 쿼리로 사용 (쿼리 1,200개) | 캡션이 붙은 사진 1장 |
| mixed | 위 두 데이터셋과 앱 레코드 194개를 한 인덱스에 합침 (레코드 6,046개, 쿼리 1,413개) | 동일 |

MIRACL 문단 파일명은 문단 ID만 사용합니다. 제목을 파일명에 넣으면 파일명 일치 가산점이 본문 검색 성능을 가리기 때문입니다.

### 결과 (2026-11-02, EmbeddingGemma 2 Q8_0)

**mixed (텍스트·사진·앱 레코드를 한 인덱스에 둔 경우)**

| 방식 | Recall@5 | Recall@10 | MRR | nDCG@10 | P@5 | 결과 없음 | 평균 결과 수 |
|---|---|---|---|---|---|---|---|
| nookive | **0.901** | **0.943** | **0.828** | **0.850** | **0.467** | 0% | 5.5 |
| cosine | 0.861 | 0.918 | 0.778 | 0.807 | 0.201 | 0% | 20 |
| keyword | 0.121 | 0.162 | 0.106 | 0.108 | 0.036 | 3.0% | 17.1 |

**mixed 안의 데이터셋별 결과 (nookive / cosine)**

| 데이터셋 | MRR | Recall@5 | P@5 | 결과 없음 |
|---|---|---|---|---|
| MIRACL-ko | 0.769 / 0.734 | 0.771 / 0.775 | 0.416 / 0.347 | 0% / 0% |
| Crossmodal-3600 | 0.839 / 0.786 | 0.924 / 0.877 | 0.476 / 0.175 | 0% / 0% |

dev와 test 분할의 차이는 모든 방식에서 0.03 이내였습니다.

### 해석

- **모달리티별 정규화는 도움이 됩니다.** 텍스트와 사진이 섞인 인덱스에서 nookive가 순수 코사인보다 MRR이 0.05 높습니다. 텍스트와 이미지는 코사인 유사도의 기준선이 달라서, 정규화 없이 섞으면 한쪽이 다른 쪽을 밀어냅니다.
- **z-score와 절대 하한만으로는 정답과 잡음이 잘 갈리지 않습니다.** 의미 게이트를 통과한 잡음과 놓친 정답 모두 z가 높고(중앙값 2.5~4) 코사인이 절대 하한 근처(±0.02)에 몰려 있습니다. 그래서 같은 모달리티 최고 코사인과의 차이(0.06 이내)를 함께 보도록 했고, 재현율을 유지하면서 P@5가 0.31 → 0.47로 올랐습니다.
- **키워드 검색만으로는 의미 검색을 대신할 수 없습니다.** 특히 한국어 캡션으로 사진을 찾는 경우 사진의 Vision 라벨과 한국어 문장이 거의 겹치지 않습니다.

### 게이트 분석 도구

`gate-analysis.test.ts`는 회귀 평가셋과 준비된 공개 데이터셋에서 게이트 조건을 바꿔 보며 지표를 비교하고, 정답을 놓친 경우와 잡음이 통과한 경우의 코사인·z-score 분포를 출력합니다. 새 규칙은 이 파일의 `variants`에 추가해 dev 분할로 고르고 test 분할로 확인합니다.

```bash
NOOKIVE_GATE_ANALYSIS=1 npx vitest run src/features/search/evaluation/gate-analysis.test.ts --silent=false
```

### 한계

- 정답은 쿼리당 판정된 항목뿐입니다. Crossmodal-3600에서는 비슷한 장면의 다른 사진도 실제로는 관련이 있을 수 있어, P@5와 잡음 비율은 실제보다 나쁘게 나옵니다. 방식 간 비교에만 사용하세요.
- 정답이 없는 쿼리는 포함하지 않았습니다. 위키백과 코퍼스에서는 "정답이 없음"을 보장하기 어렵기 때문입니다. 오탐률은 회귀 평가셋에서 확인합니다.
- 오디오·비디오·앱 이름 검색은 포함하지 않았습니다. 앱 이름 검색은 회귀 평가셋에서 확인합니다.
